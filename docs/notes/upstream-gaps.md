# Upstream gaps: Cloudflare web-bot-auth

`@posterna/core` verifies Web Bot Auth signatures with Cloudflare's open-source packages, pinned to `web-bot-auth` 0.2.0, `http-message-sig` 0.3.0 and `structured-headers` 2.0.3 (repository github.com/cloudflare/web-bot-auth, read at commit `e4d3167` on 26 October 2026). RFC 9421 parsing, signature base construction and Ed25519 verification all happen inside those packages. These are the places where we had to wrap them, and why. Each is worth raising upstream.

| # | Gap | What Posterna does | Where |
|---|---|---|---|
| 1 | `verify()` needs an explicit `label` when a request carries more than one signature, and there is no "verify any" helper. The draft (section 5.2.2) says each signature is validated on its own. | Lists the Signature-Input labels with `structured-headers`' `parseDictionary`, keeps those with `tag="web-bot-auth"`, and calls `verify()` once per label. The first that verifies wins. | `packages/core/src/verifier/signature-path.ts` |
| 2 | `verifierFromJWK()` sets the verifier's `keyid` to the key's RFC 7638 thumbprint, and `verify()` rejects a verifier whose `keyid` differs from the signed `keyid`. Live directories use other conventions: Google labels keys with short ids (`mhxuPw`), Meta publishes no kid at all. | Imports keys with `verifierFromJWK()` once, then hands `verify()` a small wrapper carrying the signed `keyid`, after selecting the key itself: by kid, then by thumbprint, then every key when the operator uses no kid. | `signature-path.ts` |
| 3 | `verify()` requires the `alg` signature parameter. The protocol draft (section 5.2) requires `created`, `expires`, `keyid` and `tag`, not `alg`, so a conformant signature without `alg` would be rejected and labeled `claimed_failed`. | When a label has no `alg`, calls `http-message-sig`'s `verifySignature()` directly and applies the same profile checks `web-bot-auth` makes (tag, bare `@authority` or `@target-uri`, Signature-Agent coverage), using `web-bot-auth`'s own `parseSignatureAgentHeader()`. Covered by the vector `signature/no-alg-parameter`. | `signature-path.ts` (`profileWithoutAlg`) |
| 4 | `maxAge` limits the time since `created`, but nothing limits the validity window (`expires - created`), which docs/SPEC.md caps at 3,600 seconds (300 until 28 October 2026). | Checks the window in `verify()`'s `validate` callback, which runs after the signature verifies. | `signature-path.ts` |
| 5 | No nonce replay store (by design: the draft leaves replay policy to deployments). | A per-instance LRU of 10,000 `(operator, keyid, nonce)` entries, checked and recorded in `validate`, so only valid signatures use a slot. | `signature-path.ts`, `lru.ts` |
| 6 | `validateNonce()` accepts only 64-byte nonces. The draft defines no nonce length (section 5.2.3 defers to RFC 9421, which has none), so a conformant signer using a shorter nonce is rejected. | Not worked around on the `alg` path: such a signature is `claimed_failed`. The no-`alg` path does not check nonce length. Worth fixing upstream rather than here. | |
| 7 | `@query-param` and the `sf`, `bs` and `tr` component parameters are not supported (`UnsupportedFeature`). The draft suggests covering `@query-param`. | Treated as a library limitation, not an invalid signature: the request fails open (`unknown_automation` with `error` set), never `claimed_failed`. Vectors `signature/unsupported-query-param` and `signature/unsupported-sf-parameter`. | `signature-path.ts` |
| 8 | Errors thrown by the verifier resolver come back wrapped as `ResolverFailed`, and policy failures from `web-bot-auth`'s own profile checks also arrive wrapped, because they run inside the resolver. | Unwraps `cause` before classifying: unknown kid, no keys, foreign Signature-Agent, invalid, or library error. | `signature-path.ts` (`unwrap`) |
| 9 | Directory response signatures (draft Appendix B) can be checked with the packages, but Posterna installs never fetch operator directories (docs/SPEC.md section 3.4), so this is not used in core. | The Posterna cloud service, which fetches directories, should verify them. | Cloud repository |

`jsonwebkey-thumbprint` 0.1.0 (pulled in by `web-bot-auth`) computes RFC 7638 thumbprints. The conformance suite checks it against the directory pipeline's thumbprints, which come from `jose`, for the three live key directories.
